## Gotchas the next agent MUST know (learned this session)
- **Dev server: port 3002** (`npm run dev`). **The agent restarted it this session — it's an agent-owned background process now** (log: `/tmp/devserver.log`). After large changes, **HMR goes stale → restart the dev server** before browser-verifying (bit us repeatedly). The user normally runs it in their own terminal; coordinate.
- **Studio iframe page-switch** needs `key={currentPage}` on the `<iframe>` (in `app/studio/page.tsx`) — changing only `src` did NOT reliably re-navigate. Fixed this session.
- **Playwright + the iframe:** `elementHandle.contentFrame()` / `frameLocator` handles go **stale** after the iframe navigates → false "element not found". Reliable approach: drive the iframe via `page.evaluate(() => document.querySelector('iframe').contentWindow.document …)` (same-origin) and poll with `page.evaluate` (NOT `waitForFunction`, which choked on the cross-frame access). See `/tmp/layout-final.mjs` for the working pattern.
- **Playwright is imported by absolute path** from the sibling beta repo: `file:///Users/nickzaremba/Documents/certainly/iwbi/onewell-standard-frontend/node_modules/playwright/index.mjs`. Always `localStorage.clear()` first; stub `/api/studio/preview` + `/api/studio/publish` to avoid real PRs.
- **Layout edits don't mutate the DOM** like text — the bridge `writeValue` for `"layout"` is a near-no-op; the section re-renders reactively from the draft store. Adding a layout to a NEW section requires: registry entry + schema enum + a `useLayoutValue`-driven variant + a `<LayoutChip>`.
- **The bridge gets field type from the DOM `data-field-type` attribute**, and the publish gate is the Zod schema (`paths.ts` is NOT in the layout path) — that's why adding `"layout"` needed no `paths.ts` change.
