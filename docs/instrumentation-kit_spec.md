# Content Studio Instrumentation Kit — design spec

> **Status (2026-07-10): DISCOVERY APPROVED — design only, nothing built.** Owner-approved via
> plan review, then amended same day (see decision log D7). Build is sequenced AFTER the
> improvement roadmap's Phase 0 machine gates (test/typecheck/CI + vendored Playwright), which
> the kit's GATE phase runs on. Owner runs and reviews everything; commits are owner-only.

## The vision in one line

**Claude Design generates marketing pages (no human designers) → every page arrives *born
editable*: marketing fine-tunes copy/images/links/styling in place via the Content Studio,
publishing through the existing per-page PR → deploy-preview → merge spine.**

One pipeline serves both page *creation* (prompting Claude Design through a generation
contract) and page *editing* (the studio overlay). The studio never needs to know a page
exists until it appears in the registry — that page-agnosticism is what makes this cheap.

## Architecture

### The per-page contract (proven pattern — live on `/`, `/page-2`, `/about` today)

A page is editable when it has: content in `lib/content/<slug>.json` · a Zod schema entry in
`lib/content/schema.ts` (the write-allowlist — content can only ever be data, never code) · a
registry entry in `lib/content/pages.ts` · JSX tagged with `data-content-path` /
`data-field-type` (+ `data-src`/`data-href`/`data-current` carriers, `data-styleable` on
block-level `<Text>`-backed nodes) · a module-scope getter destructure. `StudioMount` (root
layout) picks it up automatically once registered.

### Piece 1 — the generation contract (PRIMARY — new with D7)

A skill/prompt pack loaded by the Claude Design generation session. It makes the contract
above a *property of generation*: copy is emitted into `lib/content/<slug>.json` from the
first render, schema + tags + registry entry ship with the page, and the field vocabulary
(`text`, `richtext`, `link`, `image`, id-keyed collections as `order`; `layout`/`icon`/styling
as explicitly-declared options) is told to the generator rather than inferred afterward.

Consequences: no literal copy in JSX to go stale (the dead-JSX problem dissolves);
regeneration reads the content JSON as its copy source; marketing page *creation* becomes
"prompt Claude Design through the contract" — no separate page-builder product needed.

**Open question (pin down before build):** where does Claude Design output land — direct repo
push from its session (→ the contract ships as a repo skill, e.g. `.claude/skills/`) or
carried over manually (→ an external prompt pack). Everything else holds either way.

### Piece 2 — the instrumentation/verifier kit (demoted by D7, still required)

Two skills in `.claude/skills/`:

**`/studio-install`** — once per repo / doctor mode. Verifies or installs the studio module:
`lib/studio/*`, `components/studio/*`, the 8 API routes, `StudioMount` in the root layout, env
checklist, round-trip content test, Playwright + screenshot-diff harness. Here everything
exists → self-check. **This checklist doubles as the host contract for any future port.**

**`/instrument-page <path|route>`** — three surviving jobs:

1. **Verifier gate for every generated page:** build green · schema round-trip · edit-smoke
   e2e (enter edit mode, edit one field live, cancel restores) · then the normal PR
   deploy-preview as the human taste-check (with no designer, the preview IS the design review).
2. **Drift / regeneration handler:** when a page is regenerated or restructured, run in
   re-run mode — detect existing tags, extract only new/changed sections, apply D6
   (JSON-wins + conflict decisions), flag orphaned content paths.
3. **Fallback retrofit** for any page arriving uninstrumented, via the full pipeline:

```
1 SCOUT    parse page + section components: inventory copy/images/links/
           id-keyed collections/styleable text; detect resistant patterns
           (computed strings, animation-split text, SVG text)
2 PROPOSE  manifest — owner approves BEFORE any edit:
           path → field-type → source loc → notes, + skip list w/ reasons,
           + collection id strategy, + [OWNER-CLARIFY] judgment calls
3 APPLY    copy → JSON · Zod schema · tag JSX · registry entry ·
           richtext paths → the page-scoped sanitize list
4 GATE     build · pixel-parity screenshot diff ≤1% (retrofit must be
           visually invisible; retrofit mode only) · round-trip · edit-smoke
5 REPORT   coverage % · skips w/ reasons · diff summary → owner pushes
```

### Kit acceptance test — strip-and-rebuild

Strip a known-good page (`/page-2`, then `/about`) of its tags/registry into a fixture, run
the kit on the fixture, diff against the real page. Convergence proves the kit before it
touches a real generated page — and the fixture becomes the kit's permanent regression test.

## Steps to scale

1. **Step 0 — prerequisites:** push the 2026-07-09 publish branch-lifecycle fix; roadmap
   Phase 0 gates (the kit's GATE phase depends on them). Phase 2 build-on-branch concurrency
   and Phase 3 Cognito become load-bearing as pages/editors multiply; Phase 4 global content
   scope covers shared chrome (nav/footer) once pages share it.
2. **Step 1 — build:** generation contract + verifier gates first; retrofit mode second.
   Validate via strip-and-rebuild on the 3 existing pages.
3. **Step 2 — first real generated page** through the full pipeline; tune the contract and
   skip detection against real output.
4. **Step 3 — throughput hardening:** batch verification over N pages; rekey the layout vocab
   by (page, path) before page count makes global paths collide; `/studio` directory UX at
   20+ pages.
5. **Step 4 — automation graduation:** the same verification runs from a GitHub Action /
   scheduled agent on push, opening PRs with manifest + gate results + screenshots; owner
   still merges.
6. **Step 5 — multi-repo packaging:** out of scope per D1.

## Risks / mitigations

| Risk | Mitigation |
|---|---|
| Generated pages vary despite the contract | Verifier gates on every page; skip-don't-force; manifest for anything ambiguous |
| Regeneration vs marketing edits (drift/loss) | D6 JSON-wins + explicit conflict decisions |
| **Structural regeneration orphans content paths** (marketing's edits/styles keyed to old paths) | **#1 technical unknown — needs a focused design pass before Step 1**; D6 covers copy conflicts, not shape migrations |
| Resistant patterns (animation-split text, computed copy) | Skip + report; block-only styling ruling already fences the known traps |
| Kit quality regressing as it evolves | Strip-and-rebuild fixtures as permanent regression tests |
| More pages → more PR/branch/build traffic | Per-page sharding is designed for this; Netlify build minutes scale linearly with publish frequency (watch, don't pre-solve) |

## Deferred

Automation trigger (Step 4) · multi-repo packaging (Step 5) · per-field merge UI for
conflicts · Builder.io-class compose tooling (recedes under D7 — creation happens through the
generation contract; revisit only if prompt-driven creation proves insufficient for marketing).
