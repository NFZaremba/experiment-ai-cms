## The goal + the publish flow (the mental model)
**Goal:** let a non-technical editor change a live marketing site (text, links, formatting, soon images) and ship it, *without* touching code or git. Every change is really a git PR + Netlify deploy under the hood — that's the audit trail + rollback — but the editor only ever sees "Edit → Publish → Publish for real."

**The two-step publish flow (the core UX — don't conflate the two buttons):**
```
edit in /studio (drafts persist to localStorage)
      │
      ▼  PUBLISH
   → branch + commit landing.json + open PR  → Netlify builds a DEPLOY PREVIEW
      │                                          (production untouched)
      ▼  poll PR check status (~1–2 min)
   "Building…" → ✓ "Preview ready" (unlocks next btn) | ✕ "Build failed" (blocks it)
      │
      ▼  PUBLISH FOR REAL
   → squash-merge PR into main  → Netlify rebuilds PRODUCTION (now it's live)
```
- **Publish ≠ live.** Publish only makes a preview. **Publish for real** = merge = live.
- **Reset** = discard drafts **and** close the open PR + delete its branch (with a confirm).
- Branch-A invariant: the editor can only write `landing.json` (data), validated against the Zod schema — never code. That's what makes it safe.
